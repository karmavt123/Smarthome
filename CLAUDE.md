# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Basic Express scaffold in place. A `/api/health` route (checks DB connectivity), a `devices` CRUD slice (routes → controller → service → Prisma), and a JWT `auth` slice (sign-up, sign-in, sign-out, refresh-token — see `src/services/auth.service.js`) exist as reference patterns. Refresh tokens are stored hashed (SHA-256) in the `refresh_tokens` table and rotated on every refresh; access tokens are short-lived JWTs verified with `JWT_ACCESS_SECRET`. `src/middlewares/auth.middleware.js` exports `requireAuth`, a bearer-token guard that verifies the access token and sets `req.user`; the `devices` routes are protected with it (`router.use('/devices', requireAuth)` in `devices.routes.js` — note the path-scoped `.use`, since routers sharing the same `/api` mount prefix in `app.js` would otherwise leak an unscoped `.use` middleware into sibling routes). No Ohstem Cloud integration yet — add it as the project grows and keep this file in sync. Device pairing (`src/services/device-pairing.service.js`): `POST /api/devices/pairing-tokens` (authed, body `{ homeId }`) issues a short-lived opaque token (`PAIRING_TOKEN_TTL_MINUTES`, default 10) stored hashed (SHA-256) in the `pairing_tokens` table, same shape as `refresh_tokens`. `POST /api/devices/pair` (body `{ pairingToken, devices: [{ deviceType, deviceCode, name }] }`) redeems it — **deliberately not behind `requireAuth`**, since the token itself is the credential presented by the device/board, which has no user JWT (this is why it's registered in `devices.routes.js` *before* `router.use('/devices', requireAuth)`, the same path-scoped-`.use` ordering trick noted above). Single-use, enforced via an atomic `updateMany({ where: { used_at: null } })` inside the creating transaction so two concurrent redemptions can't both succeed; 410 if expired or already used, 404 if the token doesn't match any row. All devices in the batch are dropped into the home's first room (lowest `id`) or left unassigned if the home has no rooms yet — there's no per-device room selection in this endpoint. `devices.device_code` is **not** unique in the DB (dropped by design, migration `20260812154327_drop_device_code_unique`) — boards can be re-flashed/re-paired with the same code without a conflict. This does make `telemetry.service.js`'s `ingestBatch` device lookup by `device_code` (used when a reading POST omits `device_id`) ambiguous under duplicates — it's a `findFirst`, so it silently picks one match; fine for this school project's scale, but flag it if telemetry-by-code starts misrouting readings.

## Stack

- Runtime: Node 20 (`engines.node >=20` in package.json)
- Framework: Express 5 (`express`)
- Database: MySQL, accessed via Prisma ORM (`@prisma/client` + `prisma` CLI) — chosen over a raw driver so switching to Postgres later is a `provider` + migration change, not a rewrite
- Other deps: `cors`, `morgan` (request logging), `dotenv` (env config), `nodemon` (dev reload), `swagger-ui-express` + `swagger-jsdoc` (interactive API docs), `multer` (multipart file upload, memory storage), `axios` + `form-data` (HTTP client to the `ai-service` Face ID backend — see Face ID section below)
- Domain: school IoT project — smart home. Web server exposes an API that talks to Yolobit microcontroller boards over Ohstem Cloud (Vietnamese IoT platform commonly paired with Yolobit in education contexts).

## Commands

- Node version is pinned via `.nvmrc` (20.20.2) — run `nvm use` before anything else if your shell defaults to a different Node. Prisma 6.x's schema engine needs Node 18+ (WASM `externref` support); on Node 16 `prisma migrate`/`generate` crash with an opaque `CompileError: WebAssembly.Module()` dump. `nvm alias default` on this machine was pinned to 16.18.1 (fixed to 20.20.2 on 2026-08-12) — if it regresses, `nvm alias default 20.20.2`. In Claude Code's Bash tool specifically, each command runs in a fresh non-interactive shell that inherits a static PATH baked in when the harness started (already containing a literal `.../v16.18.1/bin` entry ahead of any nvm resolution) — plain `nvm use` in one command does not carry over to the next, and fixing the nvm default alias doesn't retroactively fix an already-inherited PATH for the running session. Prefix Node/npx/prisma commands in that context with an explicit PATH override in the same command, e.g. `PATH="$HOME/.nvm/versions/node/v20.20.2/bin:$PATH" npx prisma migrate dev --name x`.
- `npm run dev` — start server with nodemon (auto-reload)
- `npm start` — start server with plain node
- `npm test` — runs the Jest suite (per-route-slice files under `tests/`, e.g. `auth.test.js`, `devices.test.js`, `face-profiles.test.js`, `door-access-verify-face.test.js`) via Supertest against the real Express app. These are integration tests, not mocked — they hit the actual dev MySQL DB through Prisma (make sure it's running and migrated first), creating and cleaning up their own rows (unique per-run emails/device codes, `afterAll` deletes what they created). No test DB isolation yet, so don't point `DATABASE_URL` at a DB with data you can't afford to touch. The face-related test files `jest.mock('../src/services/face-id-client.service')` — they don't call the real `ai-service` (a separate Python repo, likely not running in dev/CI), they control its responses directly via `mockResolvedValueOnce`/`mockRejectedValueOnce` and assert on the Node-side business logic (DB writes, lockout, alerts) that runs around it.
- Copy `.env.example` to `.env` and fill in `DB_*` / `DATABASE_URL` / Ohstem credentials / `AI_SERVICE_URL` / `AI_SERVICE_API_KEY` before running.
- `npx prisma migrate dev --name <description>` — create + apply a migration after editing `prisma/schema.prisma` (also regenerates the client). This is the Laravel-`artisan migrate`-equivalent workflow.
- `npx prisma migrate deploy` — apply pending migrations without prompting (CI / teammate pulling new migrations)
- `npx prisma generate` — regenerate Prisma Client only, without a migration
- `npx prisma studio` — GUI to browse/edit DB rows

## Architecture

- `src/app.js` — builds and exports the Express app (middleware, route mounting) but does not listen; kept separate from the HTTP listener so tests can `require` it and drive it with Supertest without binding a real port
- `src/server.js` — entry point (`npm start`/`npm run dev` point here now): loads `.env`, requires `src/app.js`, starts the HTTP listener
- `tests/` — Jest + Supertest integration tests per route slice (`auth.test.js`, `devices.test.js`); see the `npm test` note above for how they use the real DB
- `src/config/prisma.js` — Prisma Client singleton, imported wherever DB access is needed
- `src/routes/`, `src/controllers/`, `src/services/` — layering is routes → controllers → services → `config/prisma.js` client; see the `devices` slice as the reference pattern for new resources
- `src/config/swagger.js` — builds the OpenAPI spec from `@openapi` JSDoc comments above route handlers (see `devices.routes.js`); served at `/api-docs` via Swagger UI. Add a new `@openapi` block whenever you add a route so it stays documented and testable in the browser.
- `prisma/schema.prisma` — hand-edited source of truth for DB structure (models, enums, relations). Edit this, then run `npx prisma migrate dev --name <description>` to generate + apply the migration.
- `prisma/migrations/` — one directory per migration (timestamp + name), each with the generated `migration.sql`. Committed to git; this is the DB change history, don't hand-edit past migrations.
- `db/schema.sql` — original raw-SQL schema dump, kept only as historical reference for the initial table design. No longer the source of truth — `prisma/schema.prisma` + `prisma/migrations` are canonical now. Note the `alert_rules.condition_operator` enum uses `@map` since MySQL operator values (`>`, `<`, `>=`, `<=`, `=`) aren't valid Prisma enum identifiers.
- `updated_at` columns are managed by Prisma (`@updatedAt`) at the application layer, not by a MySQL `ON UPDATE CURRENT_TIMESTAMP` trigger — only writes going through Prisma Client will bump them.
- Device communication is indirect — the backend does not talk to Yolobit boards directly; it goes through Ohstem Cloud. Isolate Ohstem Cloud API calls behind a dedicated service module (e.g. `src/services/ohstem.service.js`) so device-protocol details don't leak into route handlers. `OHSTEM_API_BASE_URL` / `OHSTEM_API_KEY` are reserved in `.env.example` for this.
- MySQL is the source of truth for persistent state (users, devices, device state/history); Ohstem Cloud is the transport to hardware, not a data store to rely on long-term.
- **`req.query` cannot be reassigned.** Express 5 made `req.query` a getter with no setter that re-parses `req.url` on every access — `req.query = ...` (and even mutating the object returned by one access) silently no-ops; a later access returns a fresh object. Query-string camelCase→snake_case conversion is done at the source instead, via `app.set('query parser', ...)` in `app.js` (wraps Node's built-in `querystring.parse` with `humps.decamelizeKeys`) — do not try to patch `req.query` in middleware or controllers again. `req.body` doesn't have this problem (it's a plain assignable property Express sets during body-parsing), so `case.middleware.js` still reassigns that one directly.

## Face ID (door unlock via face)

Implements the design in `docs/FACE-ID-PLAN-FRONTEND.md` and the ai-service integration in `docs/AI-SERVICE-FACE-ID-PLAN.md` / `docs/AI-SERVICE-FACE-ID-SPEC.md` / `docs/NODE-INTEGRATION-FOR-FACE-ID.md` (usage guide for the FE/API surface: `docs/FACE-ID-USAGE.md`).

Face detection, embedding, and liveness/anti-spoof all run in **`ai-service`, a separate Python repo** — Node holds zero AI model code. Node's job is auth, ownership, storing `face_profiles`/`door_access_logs`, lockout, PIN fallback, alerts, and issuing the door-open `device_commands`; the ai-service is "dumb" (no DB, no business logic, just AI given images in → embedding/match/liveness result out).

- `src/services/face-id-client.service.js` is the only thing in Node that talks to `ai-service`, over HTTP (`axios` + `form-data`, base URL `AI_SERVICE_URL`, auth via `X-API-Key: AI_SERVICE_API_KEY`). Exposes `isFaceIdReady()` (health check), `enrollFace(buffer, filename, contentType)` → `embedding` (512-d ArcFace vector), `verifyFace(frameBuffers, candidates, threshold)` → `{ isLive, livenessScore, matched: {id, distance} | null, distance }`, and `matchThreshold()` (reads `FACE_MATCH_THRESHOLD`).
- Error mapping in `face-id-client.service.js`: ai-service `422` (no face / multiple faces) is a real, user-facing detection problem — rethrown as `HttpError(422, ...)` and passed straight through. Everything else (`400`/`401` = Node-side bug — bad request shape or `X-API-Key` mismatch; `500`/timeout/connection refused = service down) is not the caller's fault, and is collapsed to `HttpError(503, ..., { faceIdUnavailable: true })` so callers uniformly fall back to PIN without it counting toward the face lockout counter. See the error table in `docs/NODE-INTEGRATION-FOR-FACE-ID.md` §6.
- `face_profiles.face_embedding` is nullable in the schema, and real rows with `null` exist — `POST /api/simulator/bootstrap` (`simulator.service.js`) creates a placeholder `'Demo Owner'` profile with no photo/embedding. `door-access.service.js`'s `verifyFace` must query `face_profiles` with `face_embedding: { not: null }`, not just `is_active: true` — omitting that filter previously 500'd on every call once a null-embedding profile existed in the home, because `JSON.parse(null)` doesn't throw (it coerces to the string `"null"`, which parses to the JS value `null`), so the bad row silently became `null` instead of an array. Covered by the "ignores an active face profile with no embedding" test in `tests/door-access-verify-face.test.js`.
- `face_profiles.face_embedding` (`LongText`) stores `JSON.stringify(embedding)` — a 512-number array returned by `ai-service`'s `/enroll` — never returned to clients (`face-profiles.service.js`'s `present()` strips it before serialization). **Old face-api.js embeddings (128-d) are not compatible** — every profile enrolled before the ai-service cutover had to be re-enrolled; there is no automatic migration path between embedding spaces.
- `FACE_MATCH_THRESHOLD` (env, default `0.6`) is the max Euclidean distance between two embeddings to count as a match. Node reads it and sends it to `ai-service` on every `/verify` call (Python has no hardcoded default of its own) — tune it against real enrollment photos once available.
- `src/middlewares/upload.middleware.js` exports two multer memory-storage middlewares (5MB/frame limit, jpeg/png only): `faceImageUpload` (single `image` field, used by enrollment) and `faceFramesUpload` (`images` field, 1-5 files, used by `verify-face` — multiple consecutive frames is `ai-service`'s baseline defense against video-replay spoofing per `docs/AI-SERVICE-FACE-ID-SPEC.md`).
- Uploaded enrollment photos are saved to `uploads/faces/<uuid>.<ext>` (gitignored, local disk — fine for a single-instance school project; would need object storage for multi-instance deploys) and served statically at `/uploads/faces/...` (`app.js`). `face_profiles.image_url` stores the relative filename; `src/utils/face-image-storage.js`'s `faceImageUrl(req, filename)` builds the absolute URL per-request.
- `POST /api/door-access/verify-face` (`door-access.service.js`'s `verifyFace`) does the match-and-open in one request, matching the security rationale in the plan doc: on a live match within threshold it writes `door_access_logs` and calls `device-command.service.js`'s `createDeviceCommand(..., 'open', 'face')` in the same request — callers must not separately call `/devices/:id/commands` after a `success` response. `verifyFace` builds `candidates` (`[{id, embedding}]`) from the home's active, non-null-embedding `face_profiles` and sends them to `ai-service` alongside the captured frames — ownership filtering happens in Node, `ai-service` never sees `home`/`user` concepts.
- Three outcomes from a live `ai-service` call, each handled differently: (1) `isLive: false` (spoof/replay) → `{ result: 'failed', reason: 'liveness_failed', livenessScore }`, **no** `door_access_logs` row and **not** counted toward the face lockout (a fake capture isn't a real match attempt). (2) `isLive: true` + `matched: null` (no candidate within threshold) → **does** write a failed `door_access_logs` row and **does** count toward lockout, same as the old face-api.js behavior. (3) `isLive: true` + `matched` → success path (log + device command). A `503` (ai-service unreachable/misconfigured) short-circuits before any of this and never writes a log either — see the decision table in `docs/AI-SERVICE-FACE-ID-PLAN.md` question 5 / `docs/AI-SERVICE-FACE-ID-SPEC.md` decision #5.
- Multipart routes (`face-profiles.routes.js`, the `verify-face` route in `door-access.routes.js`) decamelize `req.body` manually with `humps.decamelizeKeys` in their controllers — the global case-conversion middleware (`case.middleware.js`) only touches `req.body` when it's already an object (i.e. JSON requests parsed by `express.json()`); it runs before `multer` populates `req.body` for multipart requests, so it never sees those fields.
- `tests/fixtures/face-single-1.jpg`, `face-single-2.jpg`, `face-multi.jpg` are still committed but no longer semantically meaningful to the test suite — `face-profiles.test.js` and `door-access-verify-face.test.js` `jest.mock('../src/services/face-id-client.service')` and control `enrollFace`/`verifyFace` return values directly per scenario (no-face, multi-face, match, no-match, liveness-failed, service-unavailable), so any valid jpeg fixture works as the attached file.
- Repeated `verify-face` failures raise an alert: `alert-evaluation.service.js`'s `evaluateDoorAccessFailures(device, accessMethod)` counts `door_access_logs` rows with `result: 'failed'` for that door within a rolling window (`DOOR_FAILURE_THRESHOLD` = 3, `DOOR_FAILURE_WINDOW_MS` = 2 minutes) and, once crossed, creates an `alerts` row (`alert_type: 'unauthorized_access'`, `severity: 'critical'`) + a `notifications` row for the home's owner — same create-alert-and-notification transaction shape as `evaluateReading`'s sensor-threshold alerts. Dedup is done by checking for an existing active (`unread`/`read`) `unauthorized_access` alert whose `message` contains a `[door:<id>]` tag (there's no `device_id` column on `alerts`, so the door is tagged inline in the message text instead of a schema change) — this keeps it from creating a new alert on every failure once one is already open for that door. Wired into `door-access.service.js`'s `verifyFace` only (not the generic `POST /door-access/events` log endpoint) and scoped to `access_method: 'face'`.
- Face ID also **locks itself out** after repeated failures, forcing PIN fallback: `door-access.service.js`'s `faceLockStatus(doorDeviceId)` derives the lockout purely from `door_access_logs` (no new table/in-memory state) — it takes the most recent `FACE_LOCKOUT_THRESHOLD` (3) failed `face` attempts since the last successful one for that door, and if they're clustered within `FACE_LOCKOUT_WINDOW_MS` (2 min), the door is locked until `(newest of those 3).created_at + FACE_LOCKOUT_DURATION_MS` (5 min). `verifyFace` checks this *before* calling `ai-service` (cheap DB query first, so a locked-out caller doesn't pay the network round-trip) and throws `HttpError(423, ..., { lockedUntil })` if locked. A successful PIN unlock during the lockout does **not** clear it early — by design (per the person who requested this), Face ID stays disabled for the full 5-minute window regardless of how the door gets opened in the meantime.
- `GET /api/door-access/face-lock-status?doorDeviceId=` lets the FE poll lock state up front (`{ doorDeviceId, locked, lockedUntil }`) so it can disable the Face ID button and show a "locked until `<lockedUntil>`" message instead of letting the user hit the 423 on `verify-face`.
- PIN fallback is a real, separate flow, not just a message: `PUT /api/door-access/:doorDeviceId/pin` (body `{ pin }`, 4-8 digits) bcrypt-hashes and stores it in `door_passwords`, deactivating any previous active row for that door in the same transaction (rotation, same shape as `refresh_tokens`). `POST /api/door-access/verify-pin` (body `{ doorDeviceId, pin }`) bcrypt-compares against the door's active `door_passwords` row, logs to `door_access_logs` (`access_method: 'password'`) either way, and on match calls `device-command.service.js`'s `createDeviceCommand(..., 'open', 'password')` — same success shape as `verify-face` (`{ result, doorAccessLogId, deviceCommandId }`). No PIN configured for the door yet → `HttpError(400, ...)`, not a business-result `failed`.
- `GET /api/door-access/pin-status?doorDeviceId=` (`getPinStatusForDoor`) — `{ doorDeviceId, hasPin }`, no hash/PIN leaked. Lets the FE check "is a PIN even set for this door" without calling `verify-pin` with a throwaway guess (that would work too — `verify-pin` throws the same 400 before comparing — but this is the clean/intentional way).
